# 0002. All data access through stored procedures, called with Dapper

- Status: Accepted (supersedes the EF Core + Dapper split in the original proposal)
- Date: 2026-10-09

## Context

The team prefers SQL Server stored procedures: the SQL is visible, reviewable and tunable by a DBA,
execution plans are stable, and permissions can be granted on procedures instead of tables.
Mixing an ORM, inline SQL and procedures produces three ways to do the same thing.

## Decision

- Every read and write is a stored procedure, across the whole product: business modules, reports,
  dashboards, authentication look-ups, background jobs and health checks. No EF Core, no inline or dynamic
  SQL in C#.
- Dapper maps parameters and result sets. It is used only inside `FastXGen.Erp.Persistence.Sql`.
- Repositories (in `Persistence/Repositories/<Module>`) call `ISqlExecutor` with a `StoredProcedureName`,
  which only accepts `schema.usp_Entity_Action`. Free SQL text cannot be passed.
- Lists of child rows go in as table-valued parameters (`<schema>.<Entity>LineType`).
- The API's database login gets `EXECUTE` on schemas, not table permissions.

## Alternatives considered

- EF Core for writes, Dapper for reads (proposal): two data-access styles; migrations generated by tooling
  rather than written and reviewed SQL.
- Inline SQL with Dapper: SQL scattered through C#, harder for a DBA to review and tune.

## Consequences

- More SQL to write by hand; mitigated by the procedure template and naming convention.
- Business logic could drift into SQL; ADR 0005 draws the line.
- Integration tests must run against a real SQL Server (CI only, ADR 0011).
