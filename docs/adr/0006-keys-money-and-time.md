# 0006. Keys, money and time types

- Status: Accepted
- Date: 2026-10-09

## Context

Different records have different needs. Identity records (users, sessions) appear in tokens, links and
e-mails and may later be shared with an external identity provider, so their ids must not be guessable or
reveal how many exist. Transaction tables grow to millions of rows, where every byte in a key is repeated
in every index. People need numbers they can read out over the phone and print on documents.

## Decision: three kinds of identifier

| Kind | Used for | Type | Generated by | Example | Shown to people |
|---|---|---|---|---|---|
| **Identity key** | Users, roles, sessions/refresh tokens, terminals (devices), API keys | `UNIQUEIDENTIFIER` | `DEFAULT NEWSEQUENTIALID()` in the table | `5f1c0e2a-...` | In URLs and tokens only |
| **Record id** | Products, sales, lines, stock movements, payments, notifications... | `BIGINT IDENTITY` | The table | `120458` | Never |
| **Display number** | Documents: invoices, receipts, POs, GRNs, transfers, credit notes | `NVARCHAR(30)` | `document.usp_DocumentNumber_Next` (per tenant, branch, type, year) | `INV-BR03-2026-000123` | Always: screens, print, search |

The tenant itself has two keys:

- `TenantId INT IDENTITY`: internal, in every tenant-owned row, every index and the RLS predicate.
  Carried in the signed access token; never accepted from a client.
- `TenantKey UNIQUEIDENTIFIER`: public, used in support tools, sign-up and anything outside the token.

User-entered codes (SKU, branch code, customer code) are separate columns with a unique key per tenant.

### Rules for identity keys

- Generated by the database: the column has `DEFAULT NEWSEQUENTIALID()` and the insert procedure returns
  the value with `OUTPUT INSERTED.<Key>`. `NEWSEQUENTIALID` sorts in SQL Server's own GUID order, so the
  clustered index does not fragment. (A C# `Guid.CreateVersion7()` is time-ordered in .NET but not in
  SQL Server's sort order, and `NEWID()` is random; neither is used for keys.)
- Named like any other id (`UserId`, `RoleId`, `TerminalId`, `SessionId`); only the type differs.
  Primary key `(TenantId, <Entity>Id)`; foreign keys use the same type.
- Every column that records who did something (`CreatedByUserId`, `ApprovedByUserId`, ...) is
  `UNIQUEIDENTIFIER`.
- C# type `Guid`; validated with `ValidationRules.EntityKey()` (the empty GUID is rejected).
- Ids are identifiers, not secrets. Sequential GUIDs are partly predictable, so security never depends on
  an id being unknown: RLS, permission and scope checks protect every record. Secrets (refresh tokens,
  password-reset and invitation tokens) are 256-bit random values from `RandomNumberGenerator`, stored only
  as hashes.

### Display numbers

- `document.DocumentSequence` holds the next value per tenant, branch, document type and year, with a
  configurable pattern (`{Prefix}-{Branch}-{Year}-{Seq:000000}`).
- `document.usp_DocumentNumber_Next` reserves the next number inside the same transaction as the document
  insert (`UPDLOCK, HOLDLOCK` on the sequence row), so numbers are unique and gap-free per series.
- Unique key `(TenantId, DocumentType, DocumentNumber)`.

## Decision: money and time

| Concern | Rule |
|---|---|
| Money, quantity | `DECIMAL(18,4)`; C# `decimal`. Never `float`, `real` or `money` |
| Rates, percentages | `DECIMAL(9,6)` |
| Rounding | Explicit `MidpointRounding` per tenant/currency setting; never implicit |
| Instants | `DATETIME2(3)` in UTC, named `...AtUtc`; C# `DateTimeOffset` |
| Business dates | `DATE` (`InvoiceDate`, `ReportingDate`); C# `DateOnly` |
| Concurrency | `RowVersion ROWVERSION` on rows edited by more than one user |
| Idempotency | `ClientRequestId UNIQUEIDENTIFIER` from the client, unique per tenant |
| Soft delete | Master data only (`IsActive`, `DeactivatedAtUtc`). Transactions are never deleted (ADR 0008) |
| Text | `NVARCHAR` everywhere (multi-language), with explicit lengths |

## Alternatives considered

- GUIDs for every table: simpler rule, but 12 extra bytes per key in every index of the largest tables,
  and no benefit where records are never exposed outside the tenant.
- BIGINT for users too: compact, but user ids leak into tokens and links, reveal user counts, and would
  need remapping if an external identity provider is added.

## Consequences

- Procedures that create identity records return the key with `OUTPUT`, not `SCOPE_IDENTITY()`.
- Screens and printed documents show display numbers; record ids stay internal.
