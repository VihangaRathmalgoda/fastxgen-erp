# 0003. Database as code: SQL project, offline build, reviewed scripts

- Status: Accepted
- Date: 2026-10-09

## Context

Hand-edited databases drift between environments, and nobody knows which script ran where.
Developers work on office laptops where creating or altering databases is not allowed.

## Decision

- The schema lives in `database/FastXGen.Erp.Database` (SDK-style SQL project, `Microsoft.Build.Sql`):
  one file per object, grouped by schema (`<schema>/Tables`, `StoredProcedures`, `Functions`, `Types`, `Views`).
- `dotnet build` validates every object offline (syntax, references, types). No server is needed.
- The build outputs:
  - `FastXGen.Erp.Database.dacpac`: the versioned model of the database.
  - `FastXGen.Erp.Database_Create.sql`: an ordered script that creates a **new** database from scratch.
    It drops an existing database of the same name, so it is only for empty environments.
- Upgrades of an existing database use a script generated by comparing the dacpac with the target
  (SqlPackage `/Action:Script`), produced and reviewed by the person authorised for that environment.
- Reference data is loaded by idempotent `MERGE` scripts included from `Scripts/Script.PostDeployment.sql`.
- Database options: `PAGE_VERIFY CHECKSUM`, `READ_COMMITTED_SNAPSHOT ON`, `ALLOW_SNAPSHOT_ISOLATION ON`,
  recovery `FULL`. Target compatibility: SQL Server 2022 (`Sql160`).

## Alternatives considered

- Numbered migration scripts (DbUp/Flyway style): simple, but no offline validation of the whole model
  and procedures get copied into every migration that changes them.
- EF Core migrations: rejected with EF Core (ADR 0002).

## Consequences

- Nobody runs SQL against a shared or production database by hand.
- A PR that changes the database shows the exact `.sql` file diff for review.
- Destructive changes (dropping or narrowing a column) need a pre-deployment data script and a reviewer.
